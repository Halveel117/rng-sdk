rng_thread_bench scalability results
====================================

Spec section 6, "scalability (multithreading)". Companion to
benchmark_results.txt, which covers single-core throughput.

Two tables per machine, BOTH required, for the same reason as
benchmark_results.txt: the AES-256-CTR-DRBG row exists only in an OpenSSL
build, and the bundled HMAC baseline only in a bundled build.

  Regenerate:  ./build/rng_thread_bench          --csv <file>.csv
               ./build-openssl/rng_thread_bench  --csv <file>.csv

Defaults are 50,000,000 words per thread (HMAC rows n/25, CTR rows n/5) and
--repeats 5, median reported per cell. Raw artifacts, including the full
provenance headers and interpretive notes, are in docs/perf_x86_64/ (Machine
1) and docs/perf_arm64/ (Machine 2).

READ `efficiency`, NOT `speedup`. Efficiency is speedup / threads; 100% is
perfectly linear. The final row of each block is deliberately oversubscribed
(2x hardware threads).

====================================================================
WHAT THESE TABLES SHOW
====================================================================

1. NO SHARED-STATE CONTENTION -- the claim this tool exists to test.
   The SDK's multithreading story is that every thread owns its engine and
   nothing is shared. Two independent pieces of evidence:

   (a) The oversubscribed 32-thread row does not degrade against the
       16-thread row. Measured 32/16 aggregate ratios, all seven engine
       instances across both tables: bundled xoshiro 0.994x, pcg64
       0.997x, HMAC 1.000x; OpenSSL xoshiro 1.017x, pcg64 0.976x, CTR
       0.997x, HMAC 0.991x. All seven sit within ~2.4% of flat -- inside
       the spread already measured at those cells, so none of this is a
       decline the data can resolve.

       This is the discriminating test. Lock contention or false sharing
       degrades SUPERLINEARLY under oversubscription, because contending
       threads are descheduled while holding the contended resource; the
       signature is a collapse at 2x hardware threads. There is none.

   (b) The efficiency curve differs BY ENGINE on the same machine (at 16
       threads, bundled HMAC 57.2% vs xoshiro 47.2%). Contention on shared
       library state would fall on all engines alike, since they would be
       contending for the same thing.

   Both tables also pass the tool's stream-separation self-check, printed
   as "streams: distinct across 32 threads for every engine (verified)" --
   so the scaling measured is genuinely parallel work on distinct streams,
   not the same sequence timed N times.

2. THE 8-THREAD CELL IS THE ONE REPRODUCIBLY NOISY CELL, AND IS NOT FULLY
   DIAGNOSED. Five independent rng_thread_bench invocations were run on
   this machine while chasing this (three bundled, two OpenSSL -- the
   original attempt, a rerun, and a further rerun after manually closing
   browser and vendor tray apps). Every cell with spread > 1.3x, across
   all five runs, by thread count:

       thread count    times flagged (of 5 runs)    which engine(s)
              2                  2 of 5             pcg64 (both); hmac (1)
              8                  5 of 5             xoshiro (4); pcg64 (3);
                                                     hmac (1); ctr-drbg (1 of 2)
             32                  1 of 5             hmac (1)

   t=8 is flagged in EVERY one of the 5 attempts, by at least one engine
   -- no other thread count was flagged in more than 2 of 5, and the t=2
   and t=32 flags never repeat at the same (engine, thread) pair twice,
   which is the signature of ordinary single-run jitter rather than a
   reproducible effect. t=8 is the only cell that is genuinely
   reproducible, and no engine is categorically exempt from it -- even
   hmac-drbg, usually the cleanest, hit 1.55x at t=8 in one bundled run.

   This machine is an 8-core/16-thread part: 8 threads is exactly the
   physical-core boundary, which is a plausible reason a scheduler-
   placement effect would concentrate there specifically. Closing
   background apps did not remove it (the cleanest single run, bundled-3,
   was taken after closing apps and still flagged xoshiro@8 at 1.67x, the
   session's highest value) -- arguing against generic OS/app load as the
   sole explanation.

   The new raw-per-repeat printing (added with the warm-up patch) shows
   the SHAPE differs by engine in their noisiest runs, which matters for
   picking a cause:
     * pcg64 splits cleanly bimodal -- e.g. its worst run, OpenSSL@8:
       {6.18e9, 6.41e9} vs {4.16e9, 4.04e9, 5.41e9}, a low cluster and a
       high cluster across the 5 repeats. Consistent with SMT sibling
       scheduling: sometimes the 8 threads land on 8 distinct physical
       cores, sometimes some pair up on SMT siblings and contend for
       shared execution ports.
     * xoshiro shows one high OUTLIER per noisy run rather than a stable
       split -- e.g. its worst run, bundled@8: {9.43e9} vs {5.64e9,
       6.62e9, 6.87e9, 5.75e9}. More consistent with a one-off scheduling
       or thermal/boost-clock transition than a persistent two-state split.

   Both are plausible and this file does NOT choose between them -- doing
   so needs thread-affinity pinning plus clock monitoring, which was not
   done. Neither is a library defect, and point 1 is the reason for
   saying so. The honest statement for the report is: linear scaling to
   the physical core count is NOT demonstrated cleanly at exactly 8
   threads on this box; every other cell was clean in at least 3 of 5
   attempts, with no repeated (engine, thread) pair outside t=8. Treat
   the ARM64 machine as the cleaner test of the 8-thread boundary
   specifically.

3. NEW FINDING -- OpenSSL's HMAC path scales WORSE, not merely slower.
   Same machine, same session, HMAC-DRBG aggregate u64/s:

       threads    bundled     OpenSSL    ratio
             1   4.804e+06   3.681e+06    1.30x slower
             4   1.873e+07   1.034e+07    1.81x
            16   4.400e+07   1.856e+07    2.37x slower

   Efficiency at 16 threads: 57.2% bundled vs 31.5% OpenSSL. The penalty
   WIDENS with thread count, so it is not the constant per-call overhead
   OPEN_RESEARCH #11 records -- there is a thread-scaling component on top
   of it. A plausible mechanism is that OpenSSL's per-call provider fetch
   and MAC-context setup touch shared provider state; that mechanism is a
   HYPOTHESIS and is not verified here. The measurement is the finding.

   Consequence for #11: caching an EVP_MAC_CTX is worth more than the
   ~2x single-threaded figure suggested, because a server serving many
   concurrent sessions is exactly the workload this penalty grows in.
   Until it is fixed, the production (OpenSSL) build is the slower one for
   HMAC-DRBG, and increasingly so under load.

4. CTR-DRBG SCALES LIKE THE FAST ENGINES. 7.67x at 16 threads (47.9%),
   tracking xoshiro's 7.42x/46.4% on the same machine, and holding under
   oversubscription. AES-NI throughput parallelises across cores as
   expected; the crypto tier does not become a scaling bottleneck.
   No CTR-vs-HMAC ratio is quoted here -- see benchmark_results.txt for
   why that ratio needs care about which HMAC baseline is used.

5. NEW FINDING, ARM64 ONLY -- OpenSSL HMAC-DRBG THROUGHPUT COLLAPSES
   UNDER THREADING, not merely scales worse. This is qualitatively
   different from finding 3 above (x86_64's OpenSSL HMAC scales worse
   than bundled, but still nets positive speedup at every thread count).
   On ARM64, OpenSSL HMAC-DRBG aggregate throughput falls BELOW its
   own 1-thread number as threads increase past 4, and never recovers:

       threads    u64/s (agg)    speedup    efficiency
             1     7.074e+06       1.00x       100.0%
             2     1.087e+07       1.54x        76.8%
             4     1.352e+07       1.91x        47.8%
             8     7.590e+06       1.07x        13.4%
            14     2.758e+06       0.39x         2.8%
            28     2.704e+06       0.38x         1.4%

   28-thread throughput is ~2.6x SLOWER in absolute terms than 1-thread.
   No other engine, on either machine, does this -- every other row in
   this file has efficiency decaying but speedup staying above 1.00x.
   The bundled HMAC-DRBG row on this SAME ARM64 machine (Table 1) scales
   normally (9.63x at 28 threads), so the collapse is specific to the
   OpenSSL backend on this platform, not to HMAC-DRBG as an algorithm
   and not to the machine generally.

   Per the agreed protocol, NO CAUSE IS ASSIGNED HERE. It is recorded as
   a measurement pending investigation. It is consistent in direction
   with finding 3 (OpenSSL's HMAC path involving some form of shared or
   contended per-call state) but far more severe -- and a single shared
   cause across both platforms looks unlikely, since benchmark_results.txt
   (Machine 2 there) shows OpenSSL HMAC is *faster* than bundled HMAC
   single-threaded on this same ARM64 machine: x86_64 OpenSSL HMAC is
   slower AND scales worse; ARM64 OpenSSL HMAC is faster single-threaded
   AND collapses under threading. Two different platform-specific
   effects sharing the same OPEN_RESEARCH #11 area, not one effect
   measured twice.

6. CROSS-ARCHITECTURE, SAME-PROTOCOL COMPARISON (t=1 rows, both machines,
   both taken 2026-09-12 under the identical warm-up-patched harness):

       engine (build)              x86_64 (Ryzen)   ARM64 (M4 Pro)   ratio
       xoshiro bundled                1.358e+09        1.512e+09    1.11x ARM
       xoshiro OpenSSL                 1.381e+09        1.490e+09    1.08x ARM
       pcg64 bundled                   8.160e+08        8.613e+08    1.06x ARM
       pcg64 OpenSSL                   8.534e+08        8.596e+08    1.01x ARM
       hmac-drbg bundled               4.804e+06        5.975e+06    1.24x ARM
       hmac-drbg OpenSSL                3.681e+06        7.074e+06    1.92x ARM
       ctr-drbg OpenSSL                 9.496e+07        1.765e+08    1.86x ARM

   ARM64 leads at t=1 on every engine measured, most sharply for the two
   OpenSSL crypto rows -- consistent with finding 5's observation that
   this machine's OpenSSL crypto path behaves differently (not merely
   "slower" or "faster" but differently shaped) than the x86_64 build's.
   This is a single-thread, same-day, same-protocol comparison; it is
   NOT a substitute for benchmark_results.txt's rng_bench medians, whose
   own cross-architecture section (Machine 2 there) carries the caveat
   that its x86_64 baseline is a different, older machine and should not
   be used for a same-protocol ratio -- these t=1 rows are offered
   instead for exactly that purpose.

4.41x at 16, and the gap widens with thread count, which is the shape the
hypothesis predicted: the removed work was per-call setup touching shared
provider state, so the more threads calling it, the more it cost. Finding
(b) of 2026-09-11 is reversed on this platform. Bundled over OpenSSL was
1.29x at 1 thread and 2.42x at 16; it is now 0.36x and 0.53x, i.e. OpenSSL
is faster at every thread count measured.

WHAT THE NUMBERS DO NOT SAY. Scaling efficiency is still lower than the
bundled path (38.4% against 56.0% at 16 threads), so some per-call shared
state remains. It no longer costs enough to matter at any measured thread
count, but "improved" is not "eliminated" and the row should not be
described as contention-free.

ARM64 IS THE OPEN HALF. The 0.38x collapse at 28 threads in Table 4 was
measured on pre-fix code. The mechanism just removed is a plausible cause
and the x86_64 improvement is consistent with it, but plausible is not
measured, and #11 already warns against assuming one shared mechanism
across the two platforms. The partner re-runs rng_thread_bench and
rng_bench on the M4 Pro, OpenSSL config, before Table 4 is either trusted
or retracted.
