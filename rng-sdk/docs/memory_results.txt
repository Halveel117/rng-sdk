RNG-SDK memory consumption (spec section 6)
===========================================

Generated by `rng_memory` (tools/memory_report.cpp). This file is the header
you are reading followed, verbatim, by the stdout of that binary built in each
of the two crypto configurations:

    ./build/Release/rng_memory              -> CONFIG 1 table below
    ./build-openssl/Release/rng_memory      -> CONFIG 2 table below

BOTH backend tables are kept, for the same reason benchmark_results.txt keeps
both: the CTR-DRBG rows exist only in an OpenSSL build, so an honest
CTR-vs-HMAC footprint comparison needs the same machine twice.

Every number below was printed by the compiler that built the binary. None was
worked out by hand. sizeof is ABI-dependent (std::string and std::size_t differ
across libc++/libstdc++/MSVC and across 32- vs 64-bit), so each table is valid
only for the provenance block printed directly above it.

HEADLINE
--------
  Fast tier:     32 bytes per engine. No heap, ever.
  Crypto tier:   ~4.1 KiB per engine -- 98% of which is the 4 KiB output
                 buffer, a deliberate speed trade (drbg_engine.hpp amortises
                 the per-request Update over 4096 bytes, making NextUInt64
                 ~128x cheaper). The SP 800-90A state itself is 80 bytes
                 (HMAC) / 72 bytes (CTR).
  PF session:    120 bytes + one heap allocation per seed string.

  Nothing grows with the number of values drawn, and nothing is shared between
  threads, so the multithreaded cost is exactly one engine per thread (see
  scalability_results.txt).

Not captured by sizeof (by design, each one bounded):
  1. CtrDrbg's EVP_CIPHER_CTX -- one opaque OpenSSL heap object per
     engine, size is an OpenSSL internal and is not guessed at here.
  2. HmacDrbg::Update -- one 33-byte transient per Generate call,
     i.e. per 4096 bytes of output once buffered, not per word.
  3. pf::ByteStream / pf::ServerSession -- one heap allocation per
     seed string; 64-char hex seeds exceed every SSO threshold.
  4. NextFloats / NextInts / NextBytes(n) -- caller-sized output,
     not library overhead.

No engine allocates to produce output: the generate path is
arithmetic over fixed state, so footprint does not grow with the
number of values drawn. Per-thread cost is one engine instance
(see docs/scalability_results.txt -- no shared mutable state).
