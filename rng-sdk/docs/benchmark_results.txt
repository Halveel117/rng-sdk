rng_bench throughput results
============================

Two tables, BOTH required. The CTR-DRBG row exists only in an OpenSSL
build and the bundled HMAC baseline only in a bundled build, so an honest
CTR-vs-HMAC ratio needs the same machine twice.

Both tables below are MEDIANS over repeated runs of a single binary at a
time, produced by tools/bench_median.py. They are the measurement, not an
illustration -- ratios may be derived from them.

  Regenerate:  python tools/bench_median.py build/Release/rng_bench.exe 7
               python tools/bench_median.py build-openssl/Release/rng_bench.exe 5

One binary at a time -- never two builds back to back in one shell, which is
how the previous single-run tables were produced and why they landed OUTSIDE
the idle spread this same file documented (see THE CORRECTION, below).

DERIVED RATIOS (from the medians above)
  CTR-DRBG / bundled HMAC-DRBG = 3.196e7 / 2.485e6 = 12.9x
  OpenSSL HMAC / bundled HMAC  = 1.191e6 / 2.485e6 = 1 / 2.09

QUOTE THE CTR SPEEDUP AS "~13x", NOT TO THREE FIGURES. The bundled HMAC
denominator is what moves it: two median-of-N sessions on this same box
an hour apart gave 2.357e6 and 2.485e6, i.e. 13.6x and 12.9x from the
same CTR numerator. DESIGN_NOTES 8b's recorded 13.6x and the 2026-08-25
re-measurement's 12.9x are therefore the SAME result, not a discrepancy;
both lie inside what this hardware supports. A third figure of precision
is not measurable here.

Do NOT compare CTR-DRBG against the OpenSSL HMAC row. OpenSSL's one-shot
HMAC() is ~2x slower than the bundled reference at this call pattern (one
MAC per 32-byte block) -- see OPEN_RESEARCH #11 -- so that denominator
inflates the ratio to ~27x. That number is wrong and must not be cited.

The "C rand()" row spends five rand() calls per 64-bit word, which is how
rng_pi and rng_ode consume it; divide by 5 for a per-rand() cost. Note it
agrees to three figures across both builds (1.578e7), which is a useful
internal consistency check on the two tables.

Note: compile with -O2/Release. HMAC-DRBG cost is dominated by two
SHA-256 compressions per 32-byte block. CTR-DRBG rides AES-NI (build
-DRNGSDK_USE_OPENSSL=ON to include it; absent from Table 1 otherwise).

--------------------------------------------------------------------
THE CORRECTION, 2026-08-27
--------------------------------------------------------------------
Until this revision the two tables in this file were SINGLE runs, and
they were generated by invoking both backends back-to-back inside one
shell command -- so the two binaries contended with each other. The
result was that the tables contradicted the idle spreads printed higher
up in this same file:

  bundled hmac    table 1.294e6   vs idle range 2.025-2.257e6  (36% low)
  bundled pcg64   table 2.432e8   vs idle range 3.493-4.285e8  (30% low)
  openssl ctr     table 3.534e7   vs idle range 2.536-2.863e7  (23% high)

Taking the ratio from those two rows would have given 3.534e7 / 1.294e6
= 27x -- precisely the figure DESIGN_NOTES 8b says never to cite, arrived
at by a different route. The file also asserted that an "independent idle
re-measurement gave 14.6x -- consistent" with the 12.9x stated nine lines
above it. 12.9 and 14.6 are not consistent, and no table or spread block
anywhere in the repository supports 14.6x. Both are removed.

The lesson is the one this file already taught, applied to the file
itself: a document that states a measurement protocol and then violates
it is worse than one that states nothing, because the stated protocol is
what stops a reader checking. Tables are now medians, and the generating
script (tools/bench_median.py) runs one binary at a time by construction
so the protocol cannot be violated by hand again.

This is a genuine architecture-dependent divergence from the x86_64
result, not noise: on the x86_64/MSVC/OpenSSL build (Table 2 above and
OPEN_RESEARCH #11), OpenSSL's HMAC is ~2x SLOWER than the bundled
reference. On this ARM64/macOS build it is ~1.2x FASTER. Both halves of
this measurement are internally consistent (each table's own spread is
<=1.03x) -- the divergence is between builds/platforms, not within one.
No cause is asserted here (different OpenSSL version, different libc/
provider defaults, different underlying SHA-256 codepath are all
plausible); it is recorded as a measurement, matching the treatment
OPEN_RESEARCH #11 already gives the x86_64 side. Consequence: the ~13x
CTR-vs-HMAC figure quoted for x86_64 does NOT transfer to ARM64 -- the
ARM64 figure is ~31x, and BOTH numbers are correct for their own
platform. Do not quote one figure as "the" CTR speedup across platforms.

since-replaced 2-core development laptop (see scalability_results.txt's
toolchain note, 2026-09-11) with an older MSVC (1937). They are NOT a
same-machine, same-protocol baseline for a single-core cross-architecture
ratio against Table 3/4 -- only the two ARM64 tables are directly
comparable to each other. A same-protocol rng_bench median run on the
current x86_64 machine (Ryzen 7 260, MSVC 19.51) has not yet been taken;
until it is, cross-architecture SINGLE-CORE comparisons should rely on
scalability_results.txt's t=1 rows instead (both taken today, same
warm-up-patched harness, same protocol on both architectures).

--------------------------------------------------------------------
MEASUREMENT VALIDITY -- run this tool on an IDLE machine
--------------------------------------------------------------------
This tool is far more sensitive to machine load than to anything else.
Measured on this 2-core laptop:
  * Runs taken WHILE builds and test suites were running spanned 2.6x on
    the xoshiro uint64 row, 7.9x on xoshiro doubles, 7.0x on C rand() and
    3.9x on mt19937_64, and gave CTR-vs-HMAC ratios of 7.4x and 18.5x ten
    minutes apart. That briefly looked like evidence the hardware could
    not benchmark at all. It was not.
  * Consecutive runs on the SAME box with nothing else running span
    1.05-1.14x on most rows -- ordinary benchmark noise. A live example:
    a single run taken during an unrelated Monte Carlo job read xoshiro
    at 2.520e8 against the 6.970e8 median above, a 2.8x understatement.
The hardware is fine; concurrent load is what destroys the numbers.
So: close other work, use bench_median.py, and report median + spread.

APPENDIX, 2026-09-13: THE OPEN_RESEARCH #11 FIX, x86_64 HALF
====================================================================

Everything above this line predates the fix. Tables 1 and 2 were taken on
the retired 2-core laptop (MSVC 1937) and are kept as history; do not mix
their rows with the numbers below, which are the current Ryzen 7 260 box
(MSVC 1951, 8c/16t).

WHAT CHANGED IN THE CODE. crypto/hmac_sha256.hpp no longer calls OpenSSL's
one-shot HMAC(). It holds one EVP_MAC and one EVP_MAC_CTX per thread, with
the SHA-256 digest bound once at construction, and each call is init/update/
final on that context. No output bytes change: the OpenSSL suite passes at
895,577/895,577, the same count recorded before the change, which includes
the golden vectors and the cross-backend fingerprints.

only while #11 was open: that denominator was artificially slow, so the
ratio was inflated. It is now the SMALLER and more conservative of the two,
because it compares two OpenSSL builds rather than crossing backends.

denominator is, on which platform. The old "never cite the OpenSSL-HMAC
ratio" instruction is superseded for x86_64 post-fix builds, and the "~27x"
it warned about is dead either way: no measurement produces it any more.
