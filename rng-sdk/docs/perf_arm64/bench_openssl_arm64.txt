The CTR-vs-HMAC speedup is DELIBERATELY not printed as a fixed number
here, because it is not one. It depends on the machine's AES-NI
throughput and on WHICH HMAC baseline is used:
  * Compare CTR-DRBG against the BUNDLED HMAC row. OpenSSL's one-shot
    HMAC() is ~2x SLOWER than the bundled reference at this call
    pattern (one MAC per 32-byte block) -- see OPEN_RESEARCH #11 --
    so dividing by the OpenSSL HMAC row inflates the ratio.
  * The bundled HMAC row only exists in a BUNDLED build, and the
    CTR row only exists in an OPENSSL build, so an honest ratio needs
    BOTH builds run on the SAME machine. docs/benchmark_results.txt
    carries both tables for exactly this reason.
Recorded measurement: ~13.6x (DESIGN_NOTES 8b, MSVC Release), and an
independent idle re-measurement on 2026-08-25 gave 14.6x -- consistent.

MEASUREMENT VALIDITY -- run this tool on an IDLE machine.
This tool is far more sensitive to machine load than to anything else.
Measured on the 2-core development laptop 2026-08-25:
  * Runs taken WHILE builds and test suites were running spanned 2.6x
    on the xoshiro uint64 row, 7.9x on xoshiro doubles, 7.0x on
    C rand() and 3.9x on mt19937_64. At that spread the noise exceeds
    most of the between-engine differences the table exists to show,
    and two CTR-vs-HMAC ratios ten minutes apart gave 7.4x and 18.5x.
  * Four consecutive runs on the SAME box with nothing else running
    spanned only 1.09x (xoshiro uint64), 1.23x (pcg64), 1.11x
    (hmac-drbg) and 1.08x (C rand()) -- ordinary benchmark noise.
The hardware is fine; concurrent load is what destroys the numbers.
So: close other work, run this >=4 times, and report median + spread
rather than a single sample. A single run is evidence only once the
idle spread on that box is known. See OPEN_RESEARCH #7c(a) and #9.
