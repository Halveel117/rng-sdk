# rng-sdk

A C++17 random number library for gaming platforms, with a Provably Fair
commit-reveal scheme and verifiers a player can run without trusting the
operator. The code lives in [`rng-sdk/`](rng-sdk/); this page is the short
version.

The library has two tiers behind one API. The fast tier (xoshiro256++ and
PCG64) is for simulations and game logic where nobody needs to audit the
outcome. The cryptographic tier (HMAC-DRBG and AES-256-CTR-DRBG, both per
NIST SP 800-90A and both checked against NIST's CAVP vectors) is for anything
a player might later want to verify.

## Quick start

The SDK is header-only. Point your compiler at `rng-sdk/include` and:

```cpp
#include <rngsdk/rngsdk.hpp>

rngsdk::FastRandom   fast(42);   // xoshiro256++
rngsdk::CryptoRandom sec;        // HMAC-DRBG, seeded from the OS CSPRNG

double   d    = fast.NextDouble();   // top 53 bits, exactly uniform on [0,1)
uint64_t roll = sec.NextUInt64(6);   // [0,6), Lemire rejection, no modulo bias
```

To build the tests, tools and examples (CMake 3.16 or newer):

```
cd rng-sdk
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build --output-on-failure
```

The default build bundles its own SHA-256 and HMAC, so it needs nothing
installed. Add `-DRNGSDK_USE_OPENSSL=ON` for the production backend, which
produces the same bytes and also enables the AES-CTR-DRBG engine.

## How Provably Fair works here

Before play, the server publishes `SHA-256(server_seed)`. The player picks a
client seed. Each bet's result comes from
`HMAC-SHA256(server_seed, client_seed:nonce:cursor)`, with the nonce
increasing by one per bet and never reused. When the session ends the server
reveals the seed, and the player checks it against the commitment and
recomputes every result. `pf::ServerSession` enforces the ordering: it hands
out nonces itself, throws rather than wrap at 2^64, and refuses to play after
a reveal.

The byte derivation follows the Stake-style layout that many crypto casinos
use, so existing third-party verifiers can check our results too.

## Verifying a result

There are three verifiers, and none of them depends on the others:

- `rng_verifier`, a console tool built with the rest of the project.
- [`rng-sdk/web/verifier.html`](rng-sdk/web/verifier.html), a single HTML file
  you can open straight from disk. It makes no network requests and falls back
  to its own JavaScript SHA-256 if the browser blocks WebCrypto on `file://`.
- A C ABI (`rngsdk_c` shared or static library, one header) for integrators
  in other languages. A Python binding in `rng-sdk/bindings/python/` shows how
  to use it.

All three are tested against one set of vectors generated by an independent
Python implementation, in `rng-sdk/docs/pf_test_vectors.json`.

## Evidence

- 672,299 test checks pass on the default build and 895,577 with OpenSSL.
  Golden values come from independent implementations (Python hashlib, NumPy,
  a separate SP 800-90A implementation), not from the library itself.
- Output is byte-identical on x86-64 Windows (MSVC) and ARM64 macOS (Apple
  clang).
- Single-core throughput on an x86-64 laptop: xoshiro256++ about 7.0e8 64-bit
  words per second, PCG64 4.6e8, CTR-DRBG 3.2e7, HMAC-DRBG 2.5e6. Full tables,
  including the ARM64 machine and thread scaling, are in
  `rng-sdk/docs/benchmark_results.txt` and `scalability_results.txt`.
- Monte Carlo checks: π in 2D and 3D, and the ODE `y'' + y = 0` solved as a
  Volterra integral equation. Sound generators converge at O(1/√N). The two
  deliberately broken controls fail in different ways; LCG5's 3D estimate of
  π converges to 3.2644.

## Status

The NIST SP 800-22, Dieharder, TestU01 and PractRand runs have not happened
yet. The harness that feeds them (`rng_stream`) and the runbook are done, and
the results will go in `rng-sdk/docs/statistical_results/`. The final report
is also still to be written.
